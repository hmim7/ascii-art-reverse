# Good Practices Checklist - CLI Edition

Αυτή η σύνοψη αποτελεί το απόλυτο **Checklist Καλών Πρακτικών** (βασισμένο στους οδηγούς Core Practices & Tooling), προσαρμοσμένο ειδικά για εφαρμογές **Command Line Interface (CLI)** στην Go.

Χρησιμοποίησε αυτή τη λίστα πριν από κάθε commit ή παράδοση (audit) του CLI εργαλείου σου, για να διασφαλίσεις ότι ο κώδικάς σου είναι ιδιωματικός, καθαρός, ασφαλής και ακολουθεί τα πρότυπα της βιομηχανίας.

---

## 1. Αρχιτεκτονική & Σχεδιασμός (Clean Code, SOLID, SoC)

- [ ] **Χωρίς Global State & `init()`:** Απέφυγα τη χρήση παγκόσμιων (global) μεταβλητών και της συνάρτησης `init()` για το parsing των CLI flags.
- [ ] **Διαχωρισμός Λογικής (SoC):** Η λογική διαβάσματος και επικύρωσης των ορισμάτων (CLI arguments/flags) είναι αυστηρά διαχωρισμένη από την κύρια επιχειρησιακή λογική.
- [ ] **Ενιαία Ευθύνη (SRP):** Κάθε συνάρτηση ή δομή έχει έναν ξεκάθαρο σκοπό. Αν εντοπίσω πολλαπλές ευθύνες, τις σπάω σε μικρότερα, ανεξάρτητα τμήματα.
- [ ] **DRY & KISS:** Δεν επαναλαμβάνω λογική (Don't Repeat Yourself). Προτιμώ την απλούστερη δυνατή λύση (Keep It Simple, Stupid) και αποφεύγω τον υπερβολικό σχεδιασμό (BDUF).
- [ ] **Dependency Injection:** Οι ρυθμίσεις του CLI (π.χ. flags, paths) περνιούνται στη λογική μέσω ενός `Config` struct.
- [ ] **Ανοιχτό/Κλειστό & DI (OCP/DIP):** Ο κώδικας εξαρτάται από αφαιρέσεις (interfaces) και όχι από συγκεκριμένες υλοποιήσεις, επιτρέποντας την εύκολη προσθήκη νέων features χωρίς τροποποίηση του υπάρχοντος κώδικα.
- [ ] **Standard Library First:** Χρησιμοποίησα αποκλειστικά τη Standard Library της Go (π.χ. `flag`, `os`, `fmt`) χωρίς εξωτερικές βιβλιοθήκες (KISS & YAGNI).
- [ ] **Ονομασία Πακέτων:** Τα πακέτα μου έχουν περιγραφικά ονόματα που δηλώνουν τον σκοπό τους (απέφυγα "σκουπιδότοπους" όπως `utils`, `helpers`). Χρησιμοποιώ **σύντομα, μονολεκτικά ονόματα** χωρίς underscores ή mixedCaps.
- [ ] **Αποφυγή Stuttering:** Το όνομα του πακέτου δεν επαναλαμβάνεται στα public στοιχεία του (π.χ. `bufio.Reader`, ΟΧΙ `bufio.BufReader`).
- [ ] **Απαγόρευση `import .`:** Δεν εισάγω πακέτα με τελεία (`import .`), ώστε να είναι πάντα απολύτως σαφές από ποιο πακέτο προέρχεται κάθε συνάρτηση.
- [ ] **Blank Imports (`_`):** Περιορίζω τη χρήση του `import _ "pkg"` αποκλειστικά στη `main` ή στα tests για side-effects, και πουθενά αλλού.
- [ ] **Ασφαλής Τυχαιότητα:** Χρησιμοποιώ ΑΥΣΤΗΡΑ το `crypto/rand` (και όχι το `math/rand`) για τη δημιουργία tokens, κωδικών ή άλλων ευαίσθητων δεδομένων.

## 2. Ονοματολογία & Μορφοποίηση (Effective Go)

- [ ] **gofmt & goimports:** Έτρεξα τα εργαλεία για αυτόματη μορφοποίηση, απλοποίηση (`gofmt -s -w .`) και τακτοποίηση των imports, διασφαλίζοντας ότι η standard library διαχωρίζεται από τα εξωτερικά πακέτα με μια κενή γραμμή.
- [ ] **Αρκτικόλεξα (Initialisms):** Τα αρχικά (π.χ. `ID`, `URL`, `JSON`) είναι είτε όλα κεφαλαία είτε όλα μικρά (όχι `Id`, `Url`).
- [ ] **MixedCaps:** Γράφω τα πολυλεκτικά ονόματα (μεταβλητές, συναρτήσεις) αυστηρά με `camelCase` / `MixedCaps` και ΠΟΤΕ με `under_scores`.
- [ ] **Μικρά Ονόματα (Scope-based):** Οι τοπικές μεταβλητές σε μικρά scopes έχουν μικρά ονόματα (π.χ. `i`, `v`, `err`), ενώ οι package-level μεταβλητές είναι πιο περιγραφικές.
- [ ] **Αγκύλες & Line Length:** Δεν μεταφέρω την ανοιγόμενη αγκύλη `{` σε νέα γραμμή (ώστε να βάζει ο lexer σωστά τα semicolons). Σπάω τις μεγάλες γραμμές με βάση το νόημα (readability), όχι μηχανικά.
- [ ] **Περιττές Παρενθέσεις:** Αποφεύγω τις περιττές παρενθέσεις γύρω από τις συνθήκες στα `if`, `for` και `switch`.
- [ ] **Εκτύπωση & Debugging (fmt):** Χρησιμοποιώ σωστά τα verbs (`%v` για τιμές, `%+v` για πεδία structs, `%#v` για Go syntax, `%T` για τύπους). Στην υλοποίηση της `String()`, αποφεύγω την άπειρη αναδρομή.
- [ ] **Χωρίς `Get` στα Getters:** Αν έχω getters, δεν προσθέτω το πρόθεμα `Get` (π.χ. `cfg.Port()`, όχι `cfg.GetPort()`), ενώ στους setters το διατηρώ κανονικά (`cfg.SetPort()`).
- [ ] **Ονόματα Αποδεκτών (Receivers):** Χρησιμοποίησα 1-2 γράμματα για τα receivers (π.χ. `func (c *Config)`) και ΠΟΤΕ λέξεις όπως `this` ή `self`.
- [ ] **Συνοχή Αποδεκτών:** Δεν αναμιγνύω value και pointer receivers μέσα στον ίδιο τύπο. Επιλέγω σταθερά μία προσέγγιση.
- [ ] **Custom Output (Stringer):** Ορίζω τη μέθοδο `String() string` στα δικά μου structs για φιλική, προεπιλεγμένη εκτύπωση στο τερματικό (μέσω `fmt`).
- [ ] **Σχόλια (Godoc):** Κάθε exported συνάρτηση/struct έχει σχόλιο που είναι πλήρης πρόταση, ξεκινάει με το όνομά της, τελειώνει με τελεία και τοποθετείται **ακριβώς από πάνω**, χωρίς κενή γραμμή.

## 3. Ροή Ελέγχου & Σφάλματα (Error Handling)

- [ ] **Καμία χρήση `panic`:** Η επιχειρησιακή λογική επιστρέφει ΠΑΝΤΑ `error`. Οι κλήσεις `os.Exit(1)` ή `log.Fatal` επιτρέπονται **μόνο** μέσα στη `main()` για τον τερματισμό του CLI.
- [ ] **Guard Clauses:** Χειρίστηκα τα errors νωρίς και επέστρεψα (early return), διατηρώντας το "Happy Path" εντελώς επίπεδο (χωρίς `else` blocks).
- [ ] **Περιορισμός Scope (If Init):** Εκμεταλλεύομαι το `if` με αρχικοποίηση (`if err := ...; err != nil`) για να περιορίσω την εμβέλεια (scope) των τοπικών μεταβλητών.
- [ ] **Προτίμηση στο Switch:** Προτιμώ τη χρήση `switch` αντί για μακροσκελείς αλυσίδες `if-else if`, και εκμεταλλεύομαι τα type switches (`switch v := i.(type)`) για ασφαλή έλεγχο δυναμικών τύπων (interfaces).
- [ ] **Error Strings:** Τα κείμενα των σφαλμάτων (`fmt.Errorf`) ξεκινούν με μικρό γράμμα και ΔΕΝ τελειώνουν με τελεία.
- [ ] **Αγνόηση Σφαλμάτων:** ΔΕΝ έχω κάνει mute errors χρησιμοποιώντας το `_` εκτός κι αν υπάρχει απόλυτη βεβαιότητα ότι η συνάρτηση δεν θα αποτύχει ποτέ.
- [ ] **In-band Errors:** Αποφεύγω τη χρήση "μαγικών αριθμών" (`-1` ή `""`) για να δηλώσω λάθος. Επιστρέφω πάντα ρητά το σφάλμα ως τελευταία τιμή `(value, error)` ή `(value, ok bool)`.
- [ ] **Naked Returns:** Απέφυγα τα "γυμνά" returns (σκέτο `return` χωρίς μεταβλητές) σε συναρτήσεις μεγαλύτερες από 5 γραμμές, ακόμα κι αν χρησιμοποιώ Named Results.
- [ ] **Ασφαλές Cleanup (`defer`):** Χρησιμοποιώ την `defer` αμέσως μετά την επιτυχή δέσμευση ενός πόρου (π.χ. `os.Open`) για να διασφαλίσω το κλείσιμό του (εκτελούνται LIFO).

## 4. Δεδομένα & Διαχείριση Μνήμης (Performance)

- [ ] **Κενά Slices:** Δήλωσα τα άδεια slices ως `var data []string` (nil slice) αντί για `data := []string{}`.
- [ ] **Zero Values & Literals:** Σχεδιάζω τα structs μου ώστε η αρχική (μηδενική) τους τιμή να είναι έτοιμη για χρήση. Προτιμώ τα composite literals (`T{...}` ή `&T{...}`) και τα map literals αντί της συνάρτησης `new`.
- [ ] **Idiomatic Range:** Στα `for range` loops, παραλείπω εντελώς τη δεύτερη μεταβλητή αν δεν τη χρειάζομαι (`for k := range m` αντί για `for k, _ := range m`).
- [ ] **Capacity Προ-δέσμευση:** Όταν αρχικοποιώ Slices/Maps και ξέρω το κατά προσέγγιση μέγεθος (π.χ. από το μήκος των CLI args), χρησιμοποιώ το `make` με capacity (π.χ. `make([]string, 0, len(args))`) για αποφυγή allocations.
- [ ] **Έλεγχος Maps (Comma ok):** Χρησιμοποιώ το `v, ok := m[key]` idiom για να ελέγξω με ασφάλεια αν ένα κλειδί υπάρχει στο map, διαχωρίζοντάς το από το zero value.
- [ ] **Ασφαλής Διαγραφή (Maps):** Χρησιμοποιώ την `delete(m, key)` απευθείας, καθώς είναι ασφαλής ακόμα κι αν το κλειδί δεν υπάρχει.
- [ ] **Pointers vs Values:** Περνάω μεγάλα structs ή δομές που περιέχουν `sync.Mutex` αυστηρά ως pointers (`*`), αποφεύγοντας την αντιγραφή. Σε μικρά structs προτιμώ τα values. **Δεν** περνάω pointers σε βασικούς τύπους (`*string`, `*int`) απλώς για "εξοικονόμηση μνήμης".
- [ ] **Variadic & Append:** Όταν προσθέτω ένα slice σε άλλο, χρησιμοποιώ ιδιωματικά το `append(s, t...)`.
- [ ] **Σταθερές (Enums):** Χρησιμοποιώ το `iota` για την ασφαλή και καθαρή δήλωση enums (π.χ. modes λειτουργίας του CLI).

## 5. Διεπαφές & Εξαρτήσεις (Interfaces & DIP)

- [ ] **Δέξου Interfaces, Επίστρεψε Structs:** Οι συναρτήσεις μου (ειδικά οι constructors όπως `New()`) επιστρέφουν συγκεκριμένους τύπους και όχι interfaces. Τα interfaces τα ορίζω *μόνο* όταν τα χρειάζομαι στην πράξη (δεν τα ορίζω προκαταβολικά).
- [ ] **Μικρά Interfaces:** Ορίζω interfaces μικρά (1-2 μεθόδων) και με κατάληξη `-er` (π.χ. `Reader`, `Writer`), ΜΟΝΟ εκεί που τα χρησιμοποιώ (consumer), όχι εκεί που τα υλοποιώ.
- [ ] **Σεβασμός στα Signatures:** Δεν χρησιμοποιώ γνωστά ονόματα της Standard Library (π.χ. `Read`, `Write`, `Close`) αν η δική μου συνάρτηση έχει διαφορετική υπογραφή ή σημασία.
- [ ] **Όχι Pointers σε Interfaces:** Περνάω values, όχι pointers στα interfaces (δηλαδή `io.Reader`, ΟΧΙ `*io.Reader`).

## 6. Ταυτοχρονισμός & Context - *Αν χρησιμοποιούνται*

- [ ] **Χρήση Context:** Αν το CLI εκτελεί λειτουργίες I/O, περνάω πάντα το `context.Context` ως **πρώτη παράμετρο** στις συναρτήσεις για να ελέγχω timeouts και ακυρώσεις (π.χ. μέσω `Ctrl+C`). ΠΟΤΕ δεν το αποθηκεύω ως πεδίο μέσα σε struct.
- [ ] **Goroutine Lifetimes:** Ξέρω ακριβώς πότε και πώς τερματίζει κάθε goroutine που ξεκίνησα (μέσω Context ή `done` channels) για να αποφύγω memory leaks.
- [ ] **Σύγχρονες Συναρτήσεις:** Οι συναρτήσεις μου είναι σύγχρονες. Δίνω την επιλογή στον "caller" να αποφασίσει αν θέλει να τις τρέξει σε ξεχωριστό goroutine (δηλαδή αποφεύγω συναρτήσεις που επιστρέφουν απλά ένα channel και τρέχουν goroutines κρυφά).
- [ ] **Race Detector:** Ο κώδικας περνάει το `go test -race ./...` χωρίς κανένα απολύτως "WARNING: DATA RACE".

## 7. Δοκιμές & Ποιότητα (TDD & Automation)

- [ ] **Table-Driven Tests:** Τα tests για τη λογική του CLI είναι οργανωμένα σε μορφή πίνακα (slice of structs) με τα πεδία `name`, `input`, και `expected`.
- [ ] **Μηνύματα Αποτυχίας:** Χρησιμοποιώ `t.Errorf` αναφέροντας ξεκάθαρα τι έδωσα, τι πήρα (`got`) και τι περίμενα (`want`) με την ιδιωματική σειρά `got != want`.
- [ ] **Runnable Examples:** Για τα νέα και σημαντικά πακέτα, έχω γράψει `Example` tests που λειτουργούν ως εκτελέσιμο documentation.
- [ ] **Fuzz Testing:** Έχω γράψει έστω ένα Fuzz test για συναρτήσεις που επεξεργάζονται τα απρόβλεπτα CLI arguments ή διαβάζουν αρχεία χρήστη.
- [ ] **Test Coverage:** Στοχεύω σε υψηλό/πλήρες test coverage, καλύπτοντας επιμελώς και τα error paths.
- [ ] **Check Script:** Έτρεξα το `./check.sh` (ή `make check` ή `golangci-lint run`) και ΟΛΑ τα εργαλεία (Linting, Security, Complexity, Coverage) επέστρεψαν `[PASS]`.
