# Edge Cases: ascii-art-reverse

Boundary conditions, parser stress tests, and non-obvious behaviors that a
naive implementation is likely to get wrong. These are NOT error cases — the
program must handle all of them gracefully and produce correct output.

## Category 1: CLI Core

### X01 — Spaces and Newlines Only
**Input:** `go run . "  \n  " | cat -e`
**Expected:**
```
  $
  $
  $
  $
  $
  $
  $
  $
$
  $
  $
  $
  $
  $
  $
  $
  $
```
**Why tricky:** Two spaces produce 8 lines of 2-space-wide art; the `\n` creates a blank separator. Space glyph width must be consistent (1 column per space in standard banner).

---

### X02 — Double Backslash Before `n`
**Input:** `go run . "Hello\\nThere"`
**Expected:** "Hello" followed by a literal `\` glyph, then a newline split, then "There" — two 8-line blocks.
**Why tricky:** `\\n` must be parsed as literal-backslash + newline, NOT as the escape sequence `\n`. A naive `strings.Replace("\\n", "\n", ...)` call will get this wrong.

---

### X03 — Leading and Trailing Newlines
**Input:** `go run . "\nHello\n" standard | cat -e`
**Expected:** Blank line, 8-line "Hello", blank line.
**Why tricky:** Off-by-one: the leading `\n` creates an empty first segment; the trailing `\n` creates an empty last segment. Both must produce exactly one blank line each.

---

### X04 — Full ASCII Boundary
**Input:** `go run . " ~" standard`
**Expected:** Space glyph (1 column wide) then Tilde glyph (ASCII 126 = `(126-32)*9+1` in the banner).
**Why tricky:** Verifies correct index math at the top of the supported range.

---

### X05 — Input That Looks Like a File Path
**Input:** `go run . "../../etc/shadow" standard`
**Expected:** The string "../../etc/shadow" rendered as ASCII art using all its printable characters.
**Why tricky:** The first argument is always the text; the second is always the banner. The text content must never be interpreted as a file path.

---

### X06 — Tab Escape in Input
**Input:** `go run . "A\tB" standard`
**Expected:** "A", then 3 spaces (tab expansion), then "B" — all in one 8-line block.
**Why tricky:** The banner file has no "tab" glyph. The parser must expand `\t` to 3 spaces before any rune-to-glyph lookup.

---

### X07 — Very Long String
**Input:** `go run . "ALongStringShouldNotBreakProgram" standard`
**Expected:** One 8-line block spanning the full horizontal width; no internal newlines injected.
**Why tricky:** String builders, buffers, or line-writing loops must not add line breaks just because the art exceeds 80 columns.

---

### X08 — CRLF Line Endings
**Input:** Input argument containing `\r\n` or `\r` characters.
**Expected:** Normalized to `\n` before segment splitting; output identical to the Unix-newline version.
**Why tricky:** Windows terminals may inject `\r`; the parser must strip it before splitting.

---

### X09 — Multiple Backslashes Before `n`
**Input:** `go run . "Hello\\\\nThere"` (four backslashes + n in the shell)
**Expected:** "Hello", a literal `\` glyph, newline split, "There".
**Why tricky:** `\\\\n` in shell → `\\n` raw string → preprocess collapses `\\` to `\` then treats the remaining `n` as `\n` newline. The collapse logic must be applied left-to-right exactly once.

## Category 2: Color

### X10 — Overlapping Substring Targets
**Input:** `go run . --color=yellow "ell" --color=blue "llo" "hello"`
**Expected:** Per-rune ANSI determined by last-matching rule; the "l" at index 3 (in both "ell" and "llo") gets blue (last rule).
**Why tricky:** `buildPerRuneANSI` must iterate rules in order; later rules overwrite earlier ones at the same rune position.

---

### X11 — Repeated Target, Two Rules
**Input:** `go run . --color=red "ll" --color=green "ll" "hello"`
**Expected:** "ll" colored green (second rule overwrites first at those positions).

---

### X12 — Color with Multi-Line Input
**Input:** `go run . --color=red "Hello" "Hello\nWorld"`
**Expected:** "Hello" segment colored; "World" segment in default color.
**Why tricky:** Substring matching operates on the full input string; per-rune ANSI must be sliced correctly per segment during rendering.

---

### X13 — ANSI Codes Persisted in File
**Input:** `go run . --output=c.txt --color=red "hello"`
**Validate:** `cat -v c.txt` shows `^[[31m` before glyphs and `^[[0m` after.
**Why tricky:** ANSI bytes must be written raw (not escaped) into the file. The writer must be opened in binary mode (which `os.OpenFile` does by default in Go).

## Category 3: File System / Banner

### X14 — Doom Banner (Trailing Separator Format)
**Input:** `go run . "hello" doom`
**Expected:** Correct 8-line art using doom banner glyphs.
**Why tricky:** Doom uses trailing-separator format (`start = index×9`), not leading (`start = (index×9)+1`). The `isLeadingSeparator` heuristic must detect this correctly.

---

### X15 — Case-Insensitive Banner Name
**Input:** `go run . "hello" Standard` (uppercase S)
**Expected:** Loads `standard.txt` successfully; no warning.
**Why tricky:** `sanitizeName` must lowercase the name before lookup.

---

### X16 — Banner Name with `.txt` Extension
**Input:** `go run . "hello" standard.txt`
**Expected:** Loads `standard.txt` successfully after stripping `.txt`.

---

### X17 — Unsafe Characters in Banner Name
**Input:** `go run . "hello" "st@nd$rd"`
**Expected (stderr):** Warning about invalid/not-found banner; fallback to standard.
**Why tricky:** `@` and `$` are not in `[a-z0-9\-_]`; the sanitizer must strip them, leaving an invalid name.

## Category 4: Output

### X18 — File Overwrite (O_TRUNC Semantics)
**Steps:**
1. `go run . --output=f.txt "hello" standard`
2. `go run . --output=f.txt "world" standard`
**Expected:** `f.txt` contains only "world" art; "hello" art is gone.
**Why tricky:** `O_TRUNC` must be used, not `O_APPEND`.

---

### X19 — `COLUMNS` Environment Variable
**Input:** `COLUMNS=120 go run . --align=right "Hi"`
**Expected:** Padding calculated with width=120.
**Why tricky:** `DetectTerminalWidth` must check `COLUMNS` first, before ioctl.

---

### X20 — File Output Always Uses Width 80
**Input:** `go run . --output=f.txt --align=right "Hi"` (in a 200-column terminal)
**Expected:** Art padded to width 80, not 200.
**Why tricky:** `ResolveWidth(usingFileOutput=true)` must always return 80, ignoring terminal size.

## Category 5: Alignment

### X21 — Justify with Single Word
**Input:** `go run . --align=justify "hello" standard`
**Expected:** No panic; falls back to left alignment.
**Why tricky:** `gaps = len(words) - 1 = 0`; dividing by zero would panic. Must detect `gaps ≤ 0` and fall back.

---

### X22 — Justify Narrower Than Content
**Input:** `go run . --align=justify "hello world" standard` (with terminal width < art width)
**Expected:** Minimum 1-space gap between words; no negative spacing.
**Why tricky:** `totalGapWidth` could be ≤ 0; must enforce `baseGap = 1` as a floor.

---

### X23 — Flag After Positional Arguments
**Input:** `go run . "hello" standard --align=right`
**Expected:** "hello" right-aligned using standard banner.
**Why tricky:** `ClassifyArgs` must be position-independent; flags anywhere in `os.Args[1:]` are valid.

---

### X24 — Center With Odd-Width Art
**Input:** `go run . --align=center "hi" standard` (art width 13, terminal 80)
**Expected:** `(80 - 13) / 2 = 33` spaces on the left (integer division, no rounding).

## Category 6: Reverse

### X25 — Multi-Line Art File
**Input:** File containing two 8-line blocks separated by a blank line.
**Expected:** Output is two words joined by `\n` (e.g., `Hello\nWorld`).
**Why tricky:** The reverse pipeline must detect blank-line separators and reconstruct each row independently.

---

### X26 — Art Generated by Non-Standard Banner
**Input:** `go run . --reverse=shadow_art.txt shadow`
**Expected:** Correct string reconstruction using shadow glyph widths.
**Why tricky:** Each banner has different glyph widths; the reverse map must be built from the correct banner.

---

### X27 — Space Glyph in Art
**Input:** File containing art where the original string included spaces.
**Expected:** Spaces correctly identified and included in the output string.
**Why tricky:** The space glyph is 8 lines of empty strings; the greedy scanner must match it as a distinct character, not skip it.

---

### X28 — Reverse Combined with Banner Positional Arg
**Input:** `go run . --reverse=file.txt shadow`
**Expected:** Shadow banner used for the reverse lookup; standard is not assumed.
**Why tricky:** `main.go` must resolve the banner name from `Positional[0]` (if present alongside `--reverse`) and pass it to `reverse.Run`.

## Category 7: CLI Core - Extended

### X29 - Double-Dash as Literal String
**Input:** `go run . "--"`
**Expected:** Two hyphen glyphs rendered.
**Why tricky:** A bare `--` can be confused with the POSIX delimiter. The app must decide whether `"--"` as the only string is literal text or a fatal unknown flag, then keep docs/tests consistent.

---

### X30 - Double-Dash Delimiter
**Input:** `go run . -- "--"`
**Expected:** The first `--` is consumed as delimiter; the second `--` is rendered as text.
**Why tricky:** Once delimiter mode starts, later flag-looking tokens must never be parsed as options.

---

### X31 - Empty String vs Missing String
**Input:** `go run . ""` and `go run .`
**Expected:** `""` exits 0 with no output; no args shows usage.
**Why tricky:** Both can look like "no text" internally, but CLI intent is different.

---

### X32 - Literal `\t` After Escaped Backslash
**Input:** `go run . "A\\tB" standard`
**Expected:** `A`, literal backslash glyph, 3 expanded spaces, `B`.
**Why tricky:** Escape preprocessing must be left-to-right; `\\t` is not the same as `\t`.

---

### X33 - Trailing Single Backslash
**Input:** `go run . "abc\" standard`
**Expected:** Final backslash rendered literally.
**Why tricky:** Escape parsers often drop a final dangling escape byte.

---

### X34 - Unknown Escape Sequence
**Input:** `go run . "A\qB" standard`
**Expected:** Backslash and `q` rendered literally.
**Why tricky:** Only supported escapes should be transformed; unknown escapes must not silently delete `\`.

---

### X35 - Consecutive Escaped Newlines
**Input:** `go run . "A\n\n\nB" standard | cat -e`
**Expected:** `A` block, two blank separators between, then `B` block.
**Why tricky:** Multiple empty segments must not collapse into one.

---

### X36 - Space-Only Single Segment
**Input:** `go run . "     " standard | cat -e`
**Expected:** One 8-line block made only of spaces.
**Why tricky:** Space-only text is still renderable text, not empty input.

---

### X37 - Real Newline Mixed With Escaped Newline
**Input:** Argument containing actual LF plus literal `\n`.
**Expected:** Both produce the same segment splitting.
**Why tricky:** Shells and stdin can deliver real LF; typed CLI examples often use escaped LF.

---

### X38 - Embedded Control Bytes
**Input:** Text containing `\x00`, `\x1f`, and `\x7f`.
**Expected:** Unsupported control bytes are filtered; printable ASCII around them still renders.
